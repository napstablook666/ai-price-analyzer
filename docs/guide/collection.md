# 采集价格 📡

采集是扩展的核心动作：按站点配置请求价目，解析成「模型 + 价格 + 分组」的记录，写进 IndexedDB 快照，再由面板换算成比价表。一次刷新是一轮批处理，不是单次请求。

## 两个入口

| 入口 | 范围 | 说明 |
| --- | --- | --- |
| 面板「刷新全部」 | 当前比较模式下的启用站点 | 日常更新、改完成本口径后重算 |
| 面板「刷新当前站点」 | 筛选里选中的那一个站点 | 排查某家站、站点刚恢复；不走预检 |
| 弹窗里的刷新 | 同「刷新全部」 | 在弹窗里先做预检、再点一次确认，进度显示在弹窗里 |

同一时间只有一轮刷新。刷新进行中再点，会复用正在跑的那一轮，不会起第二条流水线。

## 先预检，再采集

`刷新全部` 之前会做一次登录态预检（`src/core/refresh-preflight.js`）：

- 只对**需要页面会话**的站点做真实请求：`mode === "page"` 且请求依赖 `pageAuth` 或 `credentials: "include"`。其余站点直接记 `无需登录`。
- 每个站点的结果归为四类：`ready`（页面会话检查通过）、`needsLogin`（401/403 或响应里出现登录页信号）、`uncertain`（连不上或状态不明）、`noLoginRequired`。
- `needsLogin` 时提示你去打开的页面手动登录；`uncertain` 会在面板里单列出来，要你自己判断。
- 预检会复用或临时打开站点标签页，临时开的 tab id 存进 `chrome.storage.session`，取消预检、预检过期或结束后关闭。
- 没有确认就发刷新请求，service worker 会回 `REFRESH_CONFIRMATION_REQUIRED`，提示你先做预检。

预检结果 5 分钟内有效（`REFRESH_PREFLIGHT_TTL_MS`），按站点签名缓存；站点列表或比较模式一变就失效，过期要重新预检。

## 一轮刷新里发生什么

1. 取当前模式下的启用站点（付费中转站或公益站，二选一）。
2. **先刷官方参考价。** 有 24 小时缓存，过期或强制时才重新拉取。这一步失败会让整轮以 error 结束，因为后面的倍数和月成本都要用它。
3. **逐站点采集**，最多 3 个站点并发（`REFRESH_CONCURRENCY = 3`）。单个站点内部按采集模式取数：接口直连，或经页面桥接让站点页面自己发请求。
4. 每个站点解析、归一后写一条快照，状态是 `success` / `partial` / `error`。
5. 通过 `REFRESH_PROGRESS` 运行消息把进度推给面板：`phase`、`total`、`completed`、当前站点、最后一条 summary。
6. 全部结束发 `phase: "complete"`，面板停止显示进度。

`partial` 表示站点返回了数据但结构不完整（缺分组比例、缺价格字段等），`core/partial-diagnostics.js` 会生成一句人话说明缺了什么。

## 失败怎么处理

- 单个站点失败只影响这一站，整轮继续。
- 失败时写一条 `status: "error"` 的快照，但**沿用上一次的** `normalized` 数据，等你修好之前表里还有旧价可看，同时带着错误文本。
- 没有自动重试，也没有断点续跑。失败就手动重刷那一站。
- service worker 被浏览器回收，进度会停在旧数字。重新打开面板不会自动接上，需要重新点一次刷新。

## 快照与新鲜度

- 每次采集写一份快照，存 IndexedDB `snapshots` 表，带 `collectedAt`、`status`、`normalizationVersion`、`normalized`。
- 写入时顺手裁剪：超过 **30 天**的旧快照删掉。
- `getSnapshots` 默认取 50 条，导出状态时取 500 条。
- 面板读的是快照，不是实时请求。打开面板不会触发采集。
- 快照是否「过期」由两件事决定（`service-worker.js` 里的 `staleAfter = 30 * 60 * 1000`）：
  - 状态不是 `success` / `partial`；
  - 或 `collectedAt` 距今超过 **30 分钟**。

  过期行在表里标灰，可以用「显示过期」开关藏起来。
- 归一化版本升级后（`NORMALIZATION_VERSION` 变了），老快照会被判定需要刷新，不参与比较。

## 官方参考价的角色

官方价与汇率是独立缓存，存在 `references` 键里，24 小时有效。它不参与「快照」，但决定表里「相对官方」列与月成本的算法。详见[官方参考价](./official-prices)。

## 手工核对

怀疑扩展算错时，按这个顺序查：

1. 站点卡片上的状态列：`success` / `partial` / `error`，以及错误文本。
2. 站点编辑弹窗里的「测试连接」：现采一次，回来一行「连接成功：N 个模型」或具体错误，`partial` 时会说缺了什么。
3. 计价单位：站点报的单价是「每 1 中转币」还是「折算成 ¥」。
4. 分组比例：某些站按分组打折，比例来自 `group_ratio`。
5. 匹配：模型是不是没对上官方价，落到「未匹配」里。

## 采集模式速查

| 模式 | 谁发请求 | 依赖 | 失败典型 |
| --- | --- | --- | --- |
| `direct` | service worker | 接口允许跨域，或有 token | CORS、401 |
| `page` | 站点页面自身（桥接） | 该站已登录的标签页 | 会话失效、标签页被关 |

两种模式都会把结果归一成同一套记录，后续流程不分模式。详见[站点配置](./stations)。
