# 成本与推荐 💰

只看单价会选错站。贵的站可能缓存便宜，便宜的站可能输出价高。扩展把单价折成月账单，再折成一条可横向比较的混合单价，推荐按混合单价判。

## 两种价格形态

每条报价有两个量：

- **计价单位价格**：站点自己的「中转单价」，分输入、缓存读取、缓存写入、输出、图片等档位。
- **折算价格**：把站点单位换算成人民币后，和基准美元价放到同一把尺子上。

充值比例决定换算系数：

```
每 1 中转币成本（¥） = 充值金额（¥） ÷ 到账中转币
```

站点按美元标注基础价时，扩展用汇率把 `USD / 1M` 转成中转币口径，再参与比较。站点配置里的「基础价 / 1M USD」和「币种已核实」就是给这一步用的。

## 月用量

「偏好与成本」里的月用量决定账单规模，界面上有 10 个输入框，外加一个预设选择：

| 字段 | 界面单位 | 说明 |
| --- | --- | --- |
| 输入 | M tokens | 每月输入 token |
| 缓存读取 | M tokens | 命中缓存的输入 token |
| 缓存写入 | M tokens | 写入缓存的 token |
| 缓存写入（1h） | M tokens | 1 小时保留期的缓存写入 |
| 输出 | M tokens | 每月输出 token |
| 请求次数 | 次 | 按次计价的站点用它 |
| 图像输入 | M tokens | 图片模型输入量 |
| 图像输出 | M tokens | 图片模型输出量 |
| 月出图张数 | 次 | 生图模型每月出图张数 |

界面上填的是百万 token，存进设置时乘回 `1,000,000`，所以内部是 token 原值。

三种取值方式（`usage-preset`）：

- **magpie-30天**：默认值，按 magpie 网关最近 30 天用量算月成本。
- **基础估算**：3000 万输入 / 600 万输出，其余为 0。
- **自定义**：用自己的用量计算。

30 天用量由扩展从本机 magpie 网关自动拉取，默认每 6 小时一次，也可以点「立即同步」手动刷新。当前使用 magpie-30天时，估算用量随同步结果更新；自定义和基础估算不被覆盖，图像用量仍保留。还没同步成功过时用内置快照（输入 326.81M、缓存读取 4434.31M、缓存写入 1.91M、输出 28.98M）。网关没开时保留上次有效值。

## 月成本怎么算

对每个参与计价的档位：

```
档位成本 = 用量（token） × 该档单价（每 M token） ÷ 1,000,000
月成本 = Σ 档位成本 + 按次计费 + 图片成本
```

站点的档位名不完全一致，扩展按语义对齐：`input`、`cache_read`、`cache_write`、`output`、`image` 等，缺失的档位按 0 计，不做猜补。

改完用量保存后，切回面板就按新值重排（面板在页面重新可见时重载）。成本是本地折算，不触发重新采集。

## 价差

```
价差 = (该站月成本 - 同模型基准月成本) ÷ 同模型基准月成本 × 100%
```

- `低 65%` 表示比基准便宜 65%，`高 20%` 表示比基准贵 20%。
- `持平` 表示和基准月成本基本一致（显示精度内）。
- 没有对上基准价的模型不显示价差，只在「显示未匹配」打开时进表。

基准月成本用的是同一套用量，所以价差只反映价格差异，不掺用量假设。颜色按价差区间区分：低于基准40% 为绿色，低 2–40% 为蓝色，接近基准为黄色，高于基准50% 为红色。

## 混合单价

月成本是「按你这套用量」的账单，不同模型可以直接比较金额，但不能据此判断价格效率。月成本长条只在同模型内按最高月成本归一，跨模型比较单位价格时看混合单价：

```
混合单价 = 月成本 ÷ 计费 token 总量 × 1,000,000
```

- 计费 token 总量 = 输入 + 缓存读取 + 缓存写入（含 1h）+ 输出 + 图像输入/输出 token。
- 请求次数、图片张数不进 token 总量，它们只体现在月成本里。
- 基准混合单价用同一套用量、同一套公式算，两者相除就是这个站的折扣倍数。
- 纯按次或纯图像的模型 token 总量为 0，不输出混合单价，不参与站点指数。

表里所有模型的混合单价都按同一个缓存/输入/输出配比混合，配比取「偏好与成本 → 估算月用量」里那一组，页面上标成 `缓存读:输入:输出` 的百分比。

站点筛选菜单里每家站点后面挂一个 `×0.62` 这样的数字，这是该站「本站混合单价 ÷ 基准混合单价」在已匹配模型上的中位数，样本不足 3 个模型不显示。

## 推荐

推荐只看月成本，不做成本与证据的加权打分。同一模型下的判定顺序是：

1. 排除不可比的行：价格缺失、非精确匹配、没有基准月成本。
2. 排除证据不足的行：匹配置信度低于设置里的推荐门槛（默认 60），标「需核验」。
3. 其余行里月成本最低的标「推荐」，再剩下标「可选」。

站点按时间段报价时，每个时段各自一行：`deepseek-flash` 原价时段一行、2 倍价时段一行，月成本按各自那一档的单价算。想看峰谷差别，看这两行的单价差即可，扩展不做加权。按秒档（视频分辨率）同理，也各自成行。

按用量分档不一样，同一个模型只出一行。上下文长度档（`<200K` / `>200K`）在表里合成一条，单价和月成本都取当前单次请求长度命中的那一档：长度取「站点画像」里的单次请求 token 数，没配就用估算月用量的平均值（计费 token 总量 ÷ 请求次数）。所以改用量或者改画像里的长度，这行会跟着换档，不会同时出现两条。

证据分来自匹配置信度本身：匹配越模糊、缓存价越是推导出来的、快照越旧，置信度越低。`estimatedFields` 会写明哪几档价格是从输入价推导的，页面在模型名下方显示「含推导：缓存读/缓存写」。

## 状态标签

报价行的状态决定它能不能进「价差」的比较，也决定它能不能进推荐：

| 标签 | 含义 | 影响 |
| --- | --- | --- |
| 部分解析：… | 快照缺计费方式、价格字段异常或有未定价模型，冒号后写明具体项 | 仍进表，计入「需核验」 |
| 价格推导 | 价格是从别的档位推出来的（`evidence: "estimated"`） | 计入「需核验」，不参与推荐 |
| 币种待核验 | 站点价格币种没在配置里确认 | 折算打折扣，置信度降低 |
| 缺少 1 小时缓存价 | 站点没有 1h 缓存写入档位 | 该档按 0 计，不影响其他档 |
| 中转价格未收录 | 站点返回里没有这一档 | 该档按 0 计 |

状态列只在公益模式下出现在表里，付费模式把这些信号放在摘要条的「需核验」和模型列的置信度里。标签都不成立时状态列留空。

## 收银台报价与结算差异

「充 300 打 9.7 折」只是第一层。从页面上的面值到微信、支付宝真正扣的钱，中间还有两层，扩展把它们分开记：

| 层 | 承载字段 | 来源 |
| --- | --- | --- |
| 面值折扣 | `rechargeTiers[].discount` | 站点 `/api/status` 的 `bulk_topup_discounts`，或插件手写 |
| 额度折人民币 | `rechargeRate` | 站点自报的 `price` / `usd_exchange_rate`，或手填 |
| 收银台金额 | `rechargePayments[]` | 点开收银台看到的应付金额，人工取证；`status=paid` 才代表已支付 |

`rechargePayments` 每项是一条付款证据：

```js
{
  channel: "alipay",     // wechat | alipay | card | stripe | crypto | other
  faceAmount: 300,       // 面值（美元额度）
  payAmount: 291,        // 收银台显示的应付金额，币种由 currency 说明
  currency: "USD",       // CNY | USD | CREDITS
  status: "pending",     // pending=未支付报价；paid=已完成支付；其他状态不参与结算折算
  paidRmb: null,         // 仅 status=paid 时填写已支付人民币；pending 报价必须为 null
  feeRate: 0.014,        // 可选，渠道手续费比例
  at: "2026-11-19",      // 取证日期
  note: "Antom 收银台待支付总额 $291.00"
}
```

月成本按这个顺序取数：

1. 有 `status=paid` 且可折算成 `paidRmb / faceAmount` 的收银台证据时，先取不超过月消耗的最大面值。所有面值都超过月消耗时取最小面值。同一面值有多个渠道时，取折算率最低的渠道。月成本 = 面值成本 × 该折算率。
2. 没有收银台证据，走档位推算：面值 × 落档折扣 × `rechargeRate`，提示带「（推算）」。
3. 两者都没有，直接按面值成本算。

只有人民币收银台金额自动等于人民币。美元或额度的 `paidRmb` 必须手填；`status=pending` 的待支付报价即使币种是 CNY，也不进排序，只在提示里显示。


这类取证只用于开发者维护插件预设。开发者要更新证据时，先读取已有 JSON 和历史订单，避免重复访问；只有缺少所需面值/渠道证据时，才定向创建一笔待支付订单，读取第三方收银台金额后立即停止。不得完成付款，也不要重复创建订单。核对后通过 `recharge:apply` 合入插件，随插件版本发布。

普通用户无需登录目标站点。扩展只使用插件内已发布的静态数据，在本地计算成本，不创建待支付订单，也不为充值证据额外请求站点。

取证脚本只在开发仓库离线运行，必须显式声明开发者操作和目标范围：

```bash
cd extension
npm run recharge:probe -- --developer --id openlux  # 定向维护优先
# 确需全量维护时：
# npm run recharge:probe -- --developer --from-plugins
npm run recharge:apply
```

全量扫描可能对多站产生请求，优先按插件 ID 或 host 定向采集。`recharge:probe` 只读取状态、充值配置和已有订单，不会创建支付订单。若所需面值/渠道缺乏证据，开发者可在站点页面人工生成一次待支付订单，读取第三方金额后停止；不得实际付款，也不要重复创建。

`recharge:apply` 幂等，重复跑不产生 diff。生成段带 `// >>> recharge-probe` 标记，手改标记内的内容下次会被覆盖。

读 `rechargePayments` 时注意：`payAmount` 的币种由 `currency` 决定，不是页面符号。不少站页面标 `$` 但实际按人民币 1:1 扣款，这种要在 `note` 里写明，别只填数字。

## 汇率

- 支持人民币与美元两种显示货币。
- 默认自动参考模式，每日更新 USD/CNY；来源为 [ExchangeRate-API](https://www.exchangerate-api.com/)，失败时切换 [Frankfurter / ECB](https://frankfurter.dev/)。
- 手动指定模式保留自己填写的汇率，刷新参考数据不会覆盖手动值。
- 拉取失败沿用上一次成功值，来源、报价日期和警告可见；完全没取到过则标为应急估算。
- 支付宝、银行卡收银台的汇率含渠道价差，单笔订单的人民币金额应录入该站充值配置，不等于通用市场参考价。
- 汇率变化只影响折算，不改站点原始价格。

## 什么时候该怀疑数字

| 症状 | 先查 |
| --- | --- |
| 月成本比站点标价高一个数量级 | 单位是每 M token 还是每 K token |
| 价差恒为 0 | 基准价没加载，模型被当成未匹配或直接回落 |
| 数字是 0 | 该档位没在站点返回里，或用量字段为 0 |
| 同一模型两行倍数差很多 | 分组或模型写法不同，匹配置信度低 |

完整误差来源和使用边界见[免责声明](../disclaimer)。
